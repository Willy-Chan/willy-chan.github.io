# Background on the MoE computation itself

![moecomp](/images/moecomputation_background.png)

- An MoE layer is meant to replace the feedfoward part of the transformer: they've run studies on this but basically you can get the same performance with much lower parameter activation
- There are multiple parts to it that make it slightly more complicated than a simple FFW (which is really just a matmul followed by pointwise activation function)
- Given some input token, you first pass it through a routing function which tells it which "expert" is going to process said token. Router itself is neural network and learned (right???)
- Each rank/GPU contains the experts, which are sharded a certain way. In this example, we assume that each rank holds 2 experts: in reality you could have any number of experts on a certain gpu, or even a single expert sharded across multiple GPUs!
- You can immediately see from the diagram the central communication issue: we need to get tokens from 1 rank to another based on which expert is assigned to it.
- Also, it's possible for a single token to get routed to multiple experts. In that case what we have to do is eventually "combine" and do a weighted sum of the token

# Naive Expert Parallelism

![a2a](/images/alltoallvisual.png)

- You've probably heard that running MoEs is an "all-to-all" workload. But I haven't (in my experience) seen many people explain what this means exactly
- First, let's go over what an all to all even is in the first place. As you can see in the diagram, it's like a "transpose" of the message and processor dimension.
- What this (famous) diagram DOESN'T capture though is the fact that the message chunk sizes don't have to be perfectly uniform! Like the triangle can be a different SIZE than the CIRCLE vs the diamond vs the square. You just have to specify the chunk size!
moedispatch
- This is the correct pattern to use for MoEs as a result: each expert is assigned a number of tokens, and each expert is associated with a GPU. Therefore, each GPU needs a certain number of tokens from all the other GPUs

![moecomp0](/images/moedispatch_0.png)
![moecomp1](/images/moedispatch_1.png)

- So you basically have to count up the tokens / expert / GPU, pack them in a tensor of the right size, and then do All-to-All accordingly.
- Note that the all-to-all operations are dedicated kernels: i.e. the CPU launched GPU kernels that perform the P2P networking operations accomplishing the A2A operation illusion.
- This was basically the paradigm before DeepEP was publically released: we rely on CPU-driven A2A kernels to do everything. But obviously there's packing overhed, and kernel launching overhead, that's not ideal.

# DeepEP and Explosion of "EP" Libraries

- The motivation behind deepEP is pretty straightforward: instead of launching an A2A from the CPU let's use NVSHMEM + IBGDA to do DEVICE-INITIATED COMMUNICATION very well
- DeepEP is just a dispatch/combine kernel that uses NVSHMEM, but it did a lot of smart things like warp specialization and handling hot experts

## Design of the DeepEP Dispatch Kernel

Here's the diagram of operations:

![moedeepep](/images/moe_deepepkernel.png)


Here's the Pseudocode:

```c
__global__ moe_dispatch_kernel() {
    int my_thread_idx = threadIdx.x;
    int warp_id = my_thread_idx / 32;
    int lane_id = my_thread_idx % 32;

    // all warps can share this shared memory:
    //     [num_toks_going_to_rank_0, num_toks_going_to_rank_1, etc...]
    __shared__ int shared_token_counts[MAX_RANKS];
    if (my_thread_idx < MAX_RANKS) {
        shared_token_counts[my_thread_idx] = 0;    // init to 0 by default
    }
    
    __syncthreads();

    // ------------------------------------------------------------------------
    // PHASE 1: WORKLOAD EXECUTION (Both warps active concurrently)
    // ------------------------------------------------------------------------
    if (warp_id == COORDINATOR_WARP_ID) {
        // coordinator warp's job is to count up the total toks per rank using shared memory atomics. We want to create the map: {r0 processes 2 toks, r1 processes 1 tok, etc.}
        for (int i = lane_id; i < num_tokens; i += 32) {   // each thread handles subset of tokens
            int target_rank = token_to_rank[i];
            atomicAdd(&shared_token_counts[target_rank], 1);  // atomic thread updates to shared memory region
        }

    } else if (warp_id == SENDER_WARP_ID) {
       // sender warp's job is to actually send the data out!

       // notice stride: each thread is sending a small share of the tokens
       for (int i = lane_id; i < num_tokens; i += 32) {   // for (token : my_share_of_tokens)
            int target_rank = token_to_rank[i];
            nvshmem_put_token_nbi(globalTokens[i], target_rank);  // async put onto NIC
        }
        // senders clear outbound network
        nvshmem_quiet();
    }
    

    __syncthreads();   // blockwise barrier; both sender and coordinator warp threads have completely finished. COORDINATOR has finished making the map, SENDER has finished putting tokens on the NIC.

    // now all that's left is for COORDINATOR to NVSHMEM_PUT his token counts onto the peer ranks so peer rank actually knows how many tokens they just got!

   // PEER RANK NEEDS TO KNOW HOW MANY TOKENS JUST GOT PUT INTO ITS MEMORY

    // ------------------------------------------------------------------------
    // PHASE 3: SIGNALING PEERS
    // ------------------------------------------------------------------------
    // Only the Coordinator Warp handles signaling, electing a single thread (lane 0)
    if (warp_id == COORDINATOR_WARP_ID && lane_id == 0) {
        
        // Loop over the remote peer ranks we counted in Phase 1
        for (int peer_rank = 0; peer_rank < MAX_RANKS; peer_rank++) {
            int total_sent = shared_token_counts[peer_rank];
            
            if (total_sent > 0) {
                // Ring the doorbell on the destination GPU
                nvshmem_atomic_add(remote_sync_counters, total_sent, peer_rank);
            }
        }
        
        // Final flush to guarantee the signal transactions clear the PCIe/NIC wires
        nvshmem_quiet();
    }
}
```

**Important Note about NVSHMEM_QUIET:** When `nvshmem_quiet` finishes, it means the network or fabric has completely delivered all your sent data into the receiver's memory (i.e. bytes have traversed the network fabric, passed through the destination network card, and are officially committed to the remote GPU's VRAM. They are legally visible to any computing core on that remote machine.). However, the *receiver doesn't know the data has arrived!*

This is because NVSHMEM is a one-sided communication model: i.e. receiver needs a signal/flag or some synchronization barrier to know it's allowed to look at the complete data.


Translation to English:
- I'm rank 0, and I'm going to launch 1 block of 2 warps: 64 threads, 32 threads / warp.

- Warp 0 is the "sender warp" and Warp 1 is the "coordinator warp"

- SENDER: thread i sends its subset of the tokens to their respective ranks in non-blocking fashion. call nvshmem_quiet() - wait until all the data has been received.

- BOTH SENDER AND COORDINATOR HIT: __syncthreads(). Sender has put all data into flight and called quiet(). Coordinator has finished counting tokens.

- COORDINATOR: 1 thread does an NVSHMEM atomic add on the number of tokens it sent on the wire, then a quiet() operation to guarantee that signal has been received.

- Receiver GPU spin waits until that atomic counter is not 0:
```
while (nvshmem_atomic_fetch(local_counter) == 0) { spin wait! }
```

- Processes the data from there.

# Why NCCL EP?

There are already a lot of MoE communication libraries out there, e.g. DeepSeek's DeepEP or Hybrid-EP. These all operate outside of NCCL and create complex deployments outside of the NVIDIA ecosystem.

- NCCL EP is just an implementation of these EP libraries, just using the standard NCCL GIN Device API, adding vendor support!
- Literally just a library that handles the dispatch and combine operations.

There is a unified API:

- `ncclEpDispatch` and `ncclEpCombine`
  - Each has:
    - Low Latency mode: 
      - Inference decode
      - Small batch sizes of 1-128 tokns
    - High Throughput mode: 
      - training and inference prefill
      - Large batch sizes of 4096+ tokens
- Replaces NVSHMEM and IBGDA kernels with standard NCCL LSA (intra-node) + GIN (inter-node)

It has better buffer management compared to DeepEP, allowing for up to 14x less memory allocation (TODO: understand).
