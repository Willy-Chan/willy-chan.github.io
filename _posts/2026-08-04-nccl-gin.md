## Background on internode communication
- RDMA lets the NIC do transfers to/from GPU memory without CPU/OS involvement
    - you talk to the NIC with the Queue Pair software interface: send queue and receive queue. These are MEMORY BUFFERS but mapped to the NIC hardware: NIC continuously monitors these for new entries (NO CPU INVOLEMENT).
    - You put WQEs into the SQ + write to a doorbell riegister (memory mapped hardware register). This triggers the NIC to read the WQE and execute the network transaction (and write to the CQ)

- Rank A allocates a QP, rank B allocates a QP, and they connect to each other. That's why it's a queue "pair"
    - a QP is POINT TO POINT: one QP per peer.
    - A QP is just some memory buffers mapped to the NIC hardware, that the NIC continuously polls/monitors.
    - a Context

- A NIC can have 100k+ QPs: QP is just some memory and a bookkeeping state on teh NIC.

- A GIN "context" is just a wrapper around 1+ QPs: GIN handles all the WQE + doorbell stuff. 
    - a "context" can reach EVERY rank, but a QP can only reach ONE rank.
    - THUS: a context must contain ONE QP PER PEER!
    - multiple contexts == a second, FULLY INDEPENDENT set of QPs to the same set of peers. 


## NCCL GIN LSA and Multimem:
- Thx to subhadeep: just an easier way to get the UVA and multimem pointer! (i.e. so you don't have to do all of the n[asty cuMemMapping yourself](https://hazyresearch.stanford.edu/blog/2025-11-17-pk))
- Once you have the UVA and multimem pointer intra-node you can just do regular CUDA UVA no issue!


Setup on the host first. The window is a LOOKUP TABLE - for each rank i, we want to know (ptr_i, rkey_i) where ptr_i is the raw memory address of rank i, rkey_i is rank i's RDMA NIC remote key permission token.

NVSHMEM: allocation and registration are the same thing. nvshmem_malloc allocates the GPU memory AND places it into the symmetric heap. THe pointer is valid across all PEs.


GIN: you can allocate memory however you want through `cudaMalloc` / PyTorch tensor buffer. AFTERWARDS, you can register it as a "window". Lets you avoid having to use nvshmem_malloc from the start!


```c++
// ============ HOST-SIDE SETUP (CPU code, runs before kernels) ============

int main(int argc, char** argv) {
    // MPI init
    // standard NCCL bootstrap using ncclUniqueId
    // standard NCCL initialization:
    ncclComm_t comm;
    ncclCommInitRank(&comm, nRanks, id, myRank);


    //////////////////// GIN SPECIFIC STUFF ////////////////////

    // GIN-specific setup of communicators
    ncclDevComm devComm;
    ncclDevCommCreate(&devComm, comm, /* enable GIN */ nullptr);


    // Rank i allocates GPU buffers like normal
    float *sendBuf, *recvBuf;
    cudaMalloc(&sendBuf, N * sizeof(float));
    cudaMalloc(&recvBuf, N * sizeof(float));

    // ... Fill the sendBuf with something valuable

    // COLLECTIVE registration: ranks call this together and exchange (pts + rkeys)
    ncclWindow_t sendWin, recvWin;
    ncclCommWindowRegister(comm, sendBuf, N * sizeof(float), &sendWin);
    ncclCommWindowRegister(comm, recvBuf, N * sizeof(float), &recvWin);


    // When launching the kernel, pass in the ncclWindow_t objects!
    ringExchange<<<1, 32>>>(devComm, sendWin, recvWin, myRank, nRanks);
    cudaDeviceSynchronize();
}
```

Here's an example of a kernel with device-side communication that you might use:

```c++
__global__ void ringExchange(ncclDevComm devComm,               // communicator group we defined
                             ncclWindow_t sendWin,              // window metadata: handles that tell you 
                             ncclWindow_t recvWin,              //          how to reach the underlying cudaMalloc buffer.
                             int myRank, int nRanks)
{
    ncclGin gin(devComm, 0);                // every gpu thread calls this constructor. It's a lightweight object that gives THIS THREAD a handle through which to issue network operations. We use context 0 (can have more contexts for more parallelism)

    int peer = (myRank + 1) % nRanks;


    // a GIN context is just "an object" that lets you initiate data transfer operations to other GPUs, and the way it does it is with QPs under the hood
    // A "context" abstracts a CHANNEL between the GPU and NIC. It's a wrapper around the QUEUE-PAIR! (QP is like a "conversation lane" between two IB NICs)
    // ORDERING IS ONLY GUARANTEED WITHIN A SINGLE (context, peer) PAIRING: NEVER ACROSS CONTEXTS! Contexts let you do stuff in PARALLEL with no guarantee of ordering.

    gin.put(...);          // uses context 0's QP
    gin.signal(...);        // uses context 0's QP
    gin.waitSignal(...);    // polls context 0's signal state
    gin.flush(...);         // flushes context 0's pending ops



    gin.put(
        ncclTeamWorld(devComm),                // communicator group
        peer,                                  // the peer I want to put into
        recvWin, myRank * N * sizeof(float),   // DST + OFFSET: I'm putting it into THEIR recvWin buffer, at offset *function of myRank*
        sendWin, 0,                            // SRC + OFFSET: I'm getting this data from MY sendWin at offset 0
        N * sizeof(float),                     // amount of data to put
        ncclGin_SignalInc{0}                   // optional: lets you signal at the very end
    );
}
```

## NCCL GIN Device API
1. DATA MOVEMENT
To do data movement, we only care about 3 core calls: `put`, `get`, and `signal`. Everything else (e.g. `putValue`) is for convenience.

```cpp
void put(
    ncclTeam team,                          // (1) which team/group of peer indices I'm looking at
    int peer,                               // (2) which rank within `team` to write into
    ncclWindow_t dstWnd,                    // (3) the PEER's registered window (where to write)
    size_t dstOffset,                       // (4) byte offset within that peer's window
    ncclWindow_t srcWnd,                    // (5) MY registered window (where to read from)
    size_t srcOffset,                       // (6) byte offset within my own window
    size_t bytes,                           // (7) how much data to move

    // ---- everything below is OPTIONAL, has defaults ----

    RemoteAction remoteAction,              // (8) what to do on the PEER once data lands
                                             //     e.g. ncclGin_StrongSignalInc{sigId}
                                             //     default: ncclGin_None (no action)

    LocalAction localAction,                // (9) what to do on MY side once the send
                                             //     is locally consumed
                                             //     e.g. ncclGin_CounterInc{counterId}
                                             //     default: ncclGin_None

    Coop coop,                              // (10) which threads are cooperating on this
                                             //      ONE call (default: ncclCoopThread —
                                             //      a single thread issues it; this is
                                             //      the recommended/normal case)

    DescriptorSmem descriptor,              // (11) scratch/staging shared memory the
                                             //      implementation may use internally
                                             //      to build the descriptor faster
                                             //      (an optimization hook, not something
                                             //      you need to reason about content-wise)

    cuda::thread_scope alreadyReleased,     // (12) a hint: "I've already done a memory
                                             //      fence up to this scope, don't redo it"
                                             //      — lets you skip redundant fencing if
                                             //      you know your data is already released
                                             //      at this scope

    cuda::thread_scope expected_scope,      // (13) the scope at which YOU need the source
                                             //      data to be visible before this put reads
                                             //      it (drives automatic fence insertion)

    SegmentType bufType                     // (14) what kind of memory the src/dst
                                             //      buffers physically are
                                             //      default: ncclGin_SegmentDevice
                                             //      (plain GPU memory — the normal case)
);

void get(
    ncclTeam team,                          // (1) same as put
    int peer,                               // (2) same as put

    ncclWindow_t remoteWnd,                 // (3) the PEER's window — SOURCE this time
    size_t remoteOffset,                    // (4) offset in their window to read from

    ncclWindow_t localWnd,                  // (5) MY window — DESTINATION this time
    size_t localOffset,                     // (6) offset in my window to write into

    size_t bytes,                           // (7) how much to pull

    // ---- optional, with defaults ----
    Coop coop = ncclCoopThread{},                        // (8) same meaning as put
    DescriptorSmem descriptor = ncclGin_None{},           // (9) same meaning as put
    uint32_t optFlags = ncclGinOptFlagsDefault,           // (10) generic flags — doc doesn't
                                                           //      enumerate what's available;
                                                           //      default is presumably fine
                                                           //      for normal use
    SegmentType bufType = ncclGin_SegmentDevice{}         // (11) same meaning as put
);

// for signal, we ONLY tell you the (team + peer) to signal. This avoids having to put(payload_size=0). 
void ncclGin::signal(
    ncclTeam team,                          // (1) same as put/get
    int peer,                               // (2) same as put/get

    RemoteAction remoteAction,              // (3) what signal to bump on the peer
                                             //     e.g. ncclGin_StrongSignalInc{0}
                                             //     — this is the WHOLE POINT of the call

    Coop coop,                              // (4) same meaning as put
    DescriptorSmem descriptor,              // (5) same meaning as put

    cuda::thread_scope alreadyReleased,     // (6) same meaning as put
    cuda::thread_scope expected_scope       // (7) same meaning as put
);
```

Example of two ranks using the signal API:
```cpp
__global__ void signalDemo(ncclDevComm devComm, int myRank)
{
    // Bind to context 0 — every rank does this the same way
    ncclGin gin(devComm, 0);

    // Signal ID 0 — an arbitrary pre-allocated "mailbox slot" both
    // ranks agree to use. Doesn't need to be "registered" like a
    // window — it's just an index into a fixed-size signal array
    // that GIN sets up per-context.
    constexpr uint32_t SIGNAL_ID = 0;

    if (myRank == 0) {
        // ---- SENDER ----
        // No data transfer at all — just tell rank 1 "bump signal 0"
        gin.signal(
            ncclTeamWorld(devComm),          // team: everyone in the communicator
            /* peer = */ 1,                  // target rank
            ncclGin_StrongSignalInc{SIGNAL_ID}  // action: increment signal 0 on rank 1
        );

        printf("Rank 0: signal sent\n");
    }

    if (myRank == 1) {
        // ---- RECEIVER ----
        // Block until signal 0's value reaches (at least) 1
        gin.waitSignal(ncclCoopThread{}, SIGNAL_ID, /* least = */ 1);

        // At this point, the increment has happened —
        // safe to assume rank 0's signal() has "landed"
        printf("Rank 1: got the signal! doing my thing now\n");

        // Reset it so it can be reused next round
        gin.resetSignal(SIGNAL_ID);
    }
}
```

2. LOCAL COMPLETION
These functions will BLOCK execution until the operations OCCURING ON MY LOCAL SIDE are fully settled and complete.
- flush / flushAsync / wait                ->   asks if ALL pending ops on this context are done.
- readCounter / waitCounter / resetCounter ->   asks if THIS SPECIFIC op/pipeline stage is done. Fine-grained per operation.

```cpp
void flush(
    Coop coop,                              // (1) which threads are jointly waiting
                                             //     here (must match how you issued
                                             //     the ops you're flushing — see below)

    cuda::memory_order ord = cuda::memory_order_acquire
                                             // (2) the memory-ordering strength applied
                                             //     once flush returns — default is
                                             //     "acquire," meaning: after this call
                                             //     returns, any subsequent reads by this
                                             //     thread are guaranteed to see the
                                             //     settled state (standard C++/CUDA
                                             //     acquire semantics)
);

// Example: pull data from a peer, then flush to know it's safe to read
ncclGin gin(devComm, 0);
gin.get(team, peer, remoteWin, 0, myWin, 0, bytes);
gin.flush(ncclCoopThread{});   // blocks until the pulled data is actually in myWin
float val = *(float*)myBufPtr;  // NOW safe to read
```
- coop is a bunch of threads, of which some of them are doing network operations.
- Past this flush call, all source PUT buffers are safe to reuse: to say nothing about the completion status on remote peers (PUT: MY SEND BUFFER IS FREE TO OVERWRITE). 
- For GET operations, this means data is visible to the local rank (THE DATA I PULLED IS NOW ACTUALLY IN MY LOCAL BUFFER).

```cpp
void flushAsync(
    ncclTeam team,                          // (1) team defining valid peer indices
    uint32_t peer,                          // (2) flush only ops targeting THIS peer
                                             //     (unlike plain flush, which covers
                                             //     everything the coop issued — this
                                             //     is scoped to one specific peer)

    ncclGinRequest_t *request,               // (3) OUT parameter: caller-provided,
                                             //     initialized by this call — this is
                                             //     the handle you'll later pass to wait()

    Coop coop = ncclCoopThread{},                     // (4) same meaning as flush
    uint32_t optFlags = ncclGinOptFlagsDefault,       // (5) generic flags, default fine
    DescriptorSmem descriptor = ncclGin_None{}        // (6) same scratch-space hook as put/get
);

ncclGinRequest_t req;
gin.flushAsync(team, peer, &req);

// ... do other useful work here while the flush is in-flight ...

gin.wait(req);   // now actually block until it's done
```
- Same thing but it's nonblocking, so the kernel can do other work.
- wait is just "now actually block" half of the flushAsync/wait pairing.


- There are also "counters" which is an alternative to flush: explanation TBD.

3. REMOTE COMPLETION
i.e. how we know stuff/completion regarding a remote peer.

```
signal      → SEND a notification to a peer (the "trigger")
waitSignal  → BLOCK until a signal reaches some value (the "receiver's wait loop")
readSignal  → PEEK at a signal's current value, don't block (the "receiver's non-blocking check")
resetSignal → CLEAR a signal back to 0 (so it can be reused next round)

// Sender:
gin.signal(team, peer, someAction);         // "hey peer, bump your signal"

// Receiver, pick one:
gin.waitSignal(coop, signalId, 1);          // block until it happens
uint64_t v = gin.readSignal(signalId);      // or just check right now, no blocking

// Receiver, cleanup:
gin.resetSignal(signalId);                  // reset to 0 for next round
```

There's more complexity in WHAT we pass in as the signal! 
- How is the signal identified? It can be a small integer ID, or a (window, offset) "VA" tuple. The latter is if the signal's locaiton needs to be computed dynamically at a specific address. Ignore VA unless your application specifically needs it.

- WEAK: only guarantees THIS SPECIFIC SIGNAL's data is visible (what you expect)
- STRONG: guarantee this signal, AS WELL AS EVERYTHING I SENT TO THIS PEER EARLIER has arrived.


4. BARRIER
No rank leaves the barrier until every rank has arrived at it.
- You construct a ncclGinBarrierSession
- Then you call .sync(...) on it to do a synchronization

```cpp
__global__ void barrierDemo(ncclDevComm devComm, int myRank)
{
    ncclGin gin(devComm, 0);

    ...
    // Every rank does DIFFERENT amounts of work here — some ranks
    // might finish fast, some slow. Doesn't matter.



    // ---- BARRIER ----
    // No rank gets past this line until EVERY rank has reached it.
    ncclGinBarrierSession bar(
        ncclCoopThread{},              // just this one thread participating
        gin,
        ncclTeamWorld(devComm),        // sync across ALL ranks
        devComm.railGinBarrier,        // where the barrier's internal state lives
        /* index = */ 0                // barrier slot id
    );
    bar.sync(ncclCoopThread{}, cuda::memory_order_acquire);



    // ---- Everyone is guaranteed to be HERE now ----
    printf("Rank %d: phase 2 starting, everyone is ready\n", myRank);
}
```
